# Boundaries

What is inside the distributable editor, what is deliberately outside it, and how each claim is
mechanically checked rather than asserted.

Companion documents: [`UPSTREAM.md`](UPSTREAM.md) (provenance and pin),
[`PATCHES.md`](PATCHES.md) (every local change to an inherited file),

## 1. The distributable boundary

The editor must build and run with **no Next.js runtime**. Two checks enforce this, and they are
deliberately different in kind.

| Check | Script | What it proves | Needs a build? |
| --- | --- | --- | --- |
| Source-level Next-import allowlist | `script/check-next-imports.mjs` | No file outside the product shell imports `next/*` | no |
| **Bundle module-graph assertion** | `script/check-distributable-boundary.mjs` | No forbidden module reached the production bundle | yes |

The second is **authoritative**. The first is fast and catches regressions at edit time, but a source
scan cannot see Next-build-time virtual modules: `content-collections` is generated by the Next build
and enters the graph through an ordinary-looking relative import, with no `next/` string anywhere on
the path.

### Why the module graph and not a text grep over the bundle

Grepping the built output for `next/image` returns two hits on a build that contains **zero** genuine
Next imports. Both are inside `@huggingface/transformers`' `convnext/image_processing_convnext.js`,
where the substring straddles `conv` + `next/image`. Minification also renames identifiers, so text
search is unsound in both directions. `apps/vite-example/build/module-graph.ts` writes
`dist/module-graph.json` from Rollup's own `this.getModuleIds()`, which is exactly "what got into the
bundle" and is diffable between builds.

### What is asserted absent

`node_modules/next/`, `apps/web/src/app/`, `apps/web/src/site/`, `apps/web/src/blog/`,
`apps/web/src/db/`, `apps/web/src/auth/`, `apps/web/src/components/landing/`,
`changelog-notification`, `content-collections`, and `apps/desktop/`.

Result on the current production build: **2,842 modules, all ten rules pass** — 549 from
`apps/web/src`, 7 from the example host, 2,282 from dependencies, 4 Vite internals.

### `src/site/` — satisfied as written, not relaxed

The editor reached into `src/site/` at the pin: `editor-header.tsx` imported `DEFAULT_LOGO_URL` and
`SOCIAL_LINKS`, `mobile-gate.tsx` imported `SITE_URL`, and `onboarding.tsx` imported `SOCIAL_LINKS`.
Three constants across four call sites.

Rather than allowlist `src/site/`, those values now enter through `EditorHost` as `branding.logoUrl`,
`links.discordUrl` and `links.roadmapUrl` (patches P-007, P-009, P-010, P-014). The Next host reads
`@/site/brand` and `@/site/social` and passes them in, so the constants keep a single source of truth
and `apps/web` renders exactly what it did at the pin; the Vite host supplies its own. Relaxing the
exclusion for three strings would have weakened a boundary that is otherwise clean.

### `apps/desktop` is excluded and is **not** a second Host

`apps/desktop` is a near-empty GPUI (Rust/Zed) experiment — roughly one source file. It is not an
alternative host of this editor, it shares no code with it, and nothing in this work targets it. It
is excluded from the bundle and asserted absent. Treating it as a second Host would imply a
portability claim that nothing here supports.

### The root `package.json` quirks are **not** repaired

The root manifest declares a self-dependency `"opencut": "."` and application dependencies `next` and
`better-auth` that belong to `apps/web` (defects D-1 and D-2 in `SBOM.md`). They are left in place,
because repairing them would be an unlogged behavioural change to the baseline this work exists to
compare against.

**This does not weaken the boundary check.** The check operates on the emitted module graph, so a
package that is *declared* but never *imported* cannot make it pass or fail. A declared-only `next`
contributes no module id. What D-2 does cause is real and recorded separately: two `next` versions
resolve, bun installs a nested copy under `apps/web/node_modules`, and the resulting type-identity
clash is why patch P-001 exists.

### Known deviation: portalled overlays remain viewport-fixed

"The editor mounts inside its root container" holds for **layout flow**. It does not hold for Radix
dialogs, dropdowns, sheets and toasts, which portal to `document.body` and position themselves
`fixed` relative to the viewport (`components/ui/{dialog,alert-dialog,sheet}.tsx`,
`components/ui/toast.tsx`).

This is a genuine embedding concern, and it is recorded rather than fixed: making overlays
container-relative would change dialog behaviour in **both** hosts, which would damage the parity
reference for no acceptance-criterion gain. An embedder that mounts the editor in a small panel today
will see dialogs centred on the browser window, not on that panel.

## 2. Export inventory

Everything `apps/vite-example` imports from the editor source. Ten modules — the surface a host
actually needs is small, which is the useful result here.

| Module | Imported | Role |
| --- | --- | --- |
| `@/core` | `EditorCore` | Editor singleton; create/open projects |
| `@/editor/host/editor-host` | `EditorHost` (type) | The host contract |
| `@/editor/host/editor-host-context` | `EditorHostProvider` | Supplies the host to the tree |
| `@/editor/surface/editor-root` | `EditorRoot` | The editor surface |
| `@/components/providers/editor-provider` | `EditorProvider` | Bootstrap: GPU, project load, font atlas |
| `@/components/editor/mobile-gate` | `MobileGate` | Small-viewport gate |
| `@/components/ui/tooltip` | `TooltipProvider` | Context the editor expects from its host |
| `@/components/ui/sonner` | `Toaster` | Toast host the editor expects |
| `@/project/types` | `TProjectMetadata` (type) | Project list rendering |
| `@/services/storage/browser-host-adapter` | `BrowserHostAdapter` | Provisional persistence boundary (§3) |

**This is not a published API.** There is no `exports` map, no entry point and no stability promise;
the example reaches in through a path alias. Designing the real export surface is later work.

### Dependencies the example had to declare explicitly

Bun hoists workspace dependencies to the root `node_modules`, so `apps/web`'s dependency closure
resolves for the example without being redeclared. Every package the example declares is therefore
either its own build tooling or a **deduplication requirement**, not a hoisting failure:

| Package | Why declared |
| --- | --- |
| `vite`, `@vitejs/plugin-react`, `vite-plugin-wasm`, `vite-plugin-top-level-await` | The example's own build tooling; `apps/web` has none of it |
| `react`, `react-dom` | Also in `apps/web` at the same range. Declared so `resolve.dedupe` has a single copy to converge on — two React copies break hooks at runtime |
| `tailwindcss`, `@tailwindcss/postcss`, `postcss` | Same versions as `apps/web`, deliberately: using the identical CSS pipeline removes "the parity difference is a CSS engine difference" as an explanation |
| `@types/react`, `@types/react-dom` | Type resolution for the example's own sources |

**No package had to be duplicated because hoisting failed.** That is a positive portability signal,
and the absence of a workaround here is worth as much as the workaround would have been.

## 3. Browser persistence — a **provisional** boundary

`apps/web/src/services/storage/browser-host-adapter.ts` is the single named place where *host* code
touches browser persistence. `script/check-storage-boundary.mjs` enforces three things: IndexedDB,
OPFS and the StorageManager quota API are called only from `apps/web/src/services/storage/`; host
code makes no direct browser-storage call; and host code demonstrably goes *through* the adapter,
because an adapter nothing imports is documentation rather than a seam.

> **No stable storage contract is published by this work.**
>
> `BrowserHostAdapter` is scaffolding. It is a facade over the existing `storageService` — no new
> behaviour, no new storage semantics, no inverted dependency. The internal adapters
> (`indexeddb-adapter.ts`, `opfs-adapter.ts`, `quota.ts`, `service.ts`) are untouched, and editor
> code still imports `storageService` directly. Only host code is required to come through the
> facade.
>
> Designing the real Host port, inverting the dependency so the editor *receives* storage instead of
> importing it, and introducing Sessions are all explicitly out of scope here. Rewiring the fifteen
> existing `storageService` importers would be that work under another name, and would put the parity
> baseline at risk for no evidential gain. **Anything built against this interface should expect it
> to change.**

One shape correction is worth recording, because it was caught by a type check rather than by review:
`storageService.getStorageInfo()` returns `{ projects, isOPFSSupported, isIndexedDBSupported }` — a
project *count*, not bytes. Byte-level figures come from `readStorageQuotaStatus()` in `quota.ts` and
are **nullable**, because `navigator.storage.estimate()` is not universally available. A host must
render "unknown" rather than a confident `0 MB`.

## 4. Runtime assets

`publicDir` is disabled. Assets are copied from `apps/web/public` by an explicit allowlist in
`apps/vite-example/build/editor-assets.ts`, and **that same list is emitted as
`dist/asset-manifest.json`** — so the allowlist *is* the manifest and there is no second inventory to
drift. An asset the editor needs but the list omits fails at runtime instead of shipping silently.

Copied: `fonts/**` (font atlas + 15 AVIF chunks), `flags/**`, `effects/preview.jpg`,
`logos/opencut/**`, and `favicon.ico` (host chrome, marked as such in the manifest). **297 files,
4.27 MB**, against 5.4 MB for all of `public/`.

Excluded with recorded reasons: `shapes/` (the shapes sticker provider generates SVG presets in code;
nothing fetches `/shapes`), `platform-guides/` (guide artwork loads from remote `cdn.brandfetch.io`),
`open-graph/`, `landing-page-dark.png`, `logos/others/`, `icons/`, `manifest.json`,
`browserconfig.xml`, `_headers`.

### A missing asset does not produce a 404

`script/check-asset-manifest.mjs` verifies every manifest entry against a running preview server, and
it deliberately does **not** judge by status code. A static SPA host answers any unknown path with
`index.html` at HTTP 200 — measured on this build, `/shapes/circle.svg`, `/platform-guides/x.png` and
`/open-graph/default.jpg` all return **200 `text/html`** despite being genuinely absent. A network
capture showing "no 404s" therefore proves much less than it appears to. The check discriminates on
`content-type` and byte length instead, and separately asserts the excluded paths *do* fall through
to the HTML fallback.

This is the same failure mode that makes a missing `/api/sounds/search` surface as a JSON parse
error rather than an HTTP failure, which is why server-backed features gate on *configured
endpoints* rather than on request failure.

### Emitted assets

The manifest also records what the bundler produced: **302 files, 30.70 MB**. The dominant entry is
`ort-wasm-simd-threaded.jsep.wasm` at **21.6 MB**, from `@huggingface/transformers` via the
transcription worker — roughly seven times `opencut_wasm_bg.wasm` (3.04 MB).

It is emitted into `dist/` but is **not on the initial load path**. Verified three ways on the
production build: the entry chunk contains zero references to it; the built `index.html` preloads
only the entry JS and CSS; and a full network capture of loading the app and opening a project never
requests it. The transcription Worker is constructed on demand inside
`services/transcription/service.ts`, so the ONNX runtime is fetched only if transcription is used.

**These are recorded measurements, not claims of adequacy.** No performance or bundle-size claim is
made anywhere in this work.

## 5. Finding: the editor crashes when no GPU is available, in **both** hosts

Spec §3.4 requires a *visible diagnostic* rather than a blank editor. Testing that path rather than
asserting it from source turned up a real defect.

Running the production build in Chrome with `--disable-gpu --disable-software-rasterizer`
(`navigator.gpu` present, WebGL2 absent), the editor mounts, renders "Loading project…", and then the
entire React tree **unmounts, leaving a blank page**. `DegradedRendererBanner` never appears, because
the tree is gone before it could render. The console shows:

```
GPU renderer unavailable: Failed to create a WebGPU surface: … webgl2 not available …
Failed to generate project thumbnail: GPU context not initialized. Call initializeGpu() first.
```

**This is upstream behaviour, not something this work introduced.** The same run against the
production `next build` + `next start` of `apps/web` fails identically, surfacing Next's built-in
*"Application error: a client-side exception has occurred"*. Both hosts run the same editor source,
and neither reaches editor chrome. The only host-attributable difference was that Next ships a
framework-level error boundary and a bare Vite host does not.

So the example gained `src/editor-error-boundary.tsx` — **host code only, no change to editor
behaviour**. It catches the crash and shows the error message plus `window.__wasmPanic` if one was
recorded, which restores §3.4's "visible diagnostic instead of a blank editor" for this host. It
deliberately does not attempt to prevent or recover from the crash; doing so would change editor
behaviour and cost the parity reference.

Two things remain unverified and should not be read as passing:

- **`DegradedRendererBanner` has never been observed.** Reaching it requires `isGpuAvailable()` to be
  false *without* the bootstrap crashing first, and no configuration producing that has been found.
- **The `window.__wasmPanic` channel has never been triggered.** It was readable throughout (value
  `null`), but this failure is a WebGPU *surface* error, not a Rust panic, so nothing ever wrote to
  it. The channel's plumbing is intact; its end-to-end behaviour is untested.
