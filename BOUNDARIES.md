# Boundaries

What is inside the distributable editor, what is deliberately outside it, and how each claim is
mechanically checked rather than asserted.

Companion documents: [`UPSTREAM.md`](UPSTREAM.md) (provenance and pin),
[`PATCHES.md`](PATCHES.md) (every local change to an inherited file),
[`SBOM.md`](SBOM.md) (dependencies and known upstream metadata defects),

[`FEATURE_HANDLING.md`](FEATURE_HANDLING.md) (what each server- or network-dependent feature does
without a server), and [`PARITY.md`](PARITY.md) (the two-host editing-parity deviation report).

## 1. The distributable boundary

The editor must build and run with **no Next.js runtime**. Two checks enforce this, and they are
deliberately different in kind.

| Check                              | Script                                    | What it proves                                     | Needs a build? |
| ---------------------------------- | ----------------------------------------- | -------------------------------------------------- | -------------- |
| Source-level Next-import allowlist | `script/check-next-imports.mjs`           | No file outside the product shell imports `next/*` | no             |
| **Bundle module-graph assertion**  | `script/check-distributable-boundary.mjs` | No forbidden module reached the production bundle  | yes            |

The second is **authoritative**. The first is fast and catches regressions at edit time, but a source
scan cannot see Next-build-time virtual modules: `content-collections` is generated by the Next build
and enters the graph through an ordinary-looking relative import, with no `next/` string anywhere on
the path.

### Why the module graph and not a text grep over the bundle

Grepping the built output for `next/image` returns two hits on a build that contains **zero** genuine
Next imports. Both are inside `@huggingface/transformers`' `convnext/image_processing_convnext.js`,
where the substring straddles `conv` + `next/image`. Minification also renames identifiers, so text
search is unsound in both directions. `apps/vite-example/build/module-graph.ts` writes
`dist/module-graph.json` from Rollup's own `this.getModuleIds()`, which is exactly "what got into the
bundle" and is diffable between builds.

### What is asserted absent

`node_modules/next/`, `apps/web/src/app/`, `apps/web/src/site/`, `apps/web/src/blog/`,
`apps/web/src/db/`, `apps/web/src/auth/`, `apps/web/src/components/landing/`,
`changelog-notification`, `content-collections`, and `apps/desktop/`.

Result on the current production build: **2,931 modules, all ten rules pass** — 630 from
`apps/web/src`, 15 from the example host, 2,282 from dependencies, 4 other/Vite modules. This is
the final two-entry graph described below; the evidence-only entry is counted because Rollup emits
it in the same build, even though the ordinary app does not link to it.

### `src/site/` — satisfied as written, not relaxed

The editor reached into `src/site/` at the pin: `editor-header.tsx` imported `DEFAULT_LOGO_URL` and
`SOCIAL_LINKS`, `mobile-gate.tsx` imported `SITE_URL`, and `onboarding.tsx` imported `SOCIAL_LINKS`.
Three constants across four call sites.

Rather than allowlist `src/site/`, those values now enter through `EditorHost` as `branding.logoUrl`,
`links.discordUrl` and `links.roadmapUrl` (patches P-007, P-009, P-010, P-014). The Next host reads
`@/site/brand` and `@/site/social` and passes them in, so the constants keep a single source of truth
and `apps/web` renders exactly what it did at the pin; the Vite host supplies its own. Relaxing the
exclusion for three strings would have weakened a boundary that is otherwise clean.

### `apps/desktop` is excluded and is **not** a second Host

`apps/desktop` is a near-empty GPUI (Rust/Zed) experiment — roughly one source file. It is not an
alternative host of this editor, it shares no code with it, and nothing in this work targets it. It
is excluded from the bundle and asserted absent. Treating it as a second Host would imply a
portability claim that nothing here supports.

### The root `package.json` quirks are **not** repaired

The root manifest declares a self-dependency `"opencut": "."` and application dependencies `next` and
`better-auth` that belong to `apps/web` (defects D-1 and D-2 in `SBOM.md`). They are left in place,
because repairing them would be an unlogged behavioural change to the baseline this work exists to
compare against.

**This does not weaken the boundary check.** The check operates on the emitted module graph, so a
package that is _declared_ but never _imported_ cannot make it pass or fail. A declared-only `next`
contributes no module id. What D-2 does cause is real and recorded separately: two `next` versions
resolve, bun installs a nested copy under `apps/web/node_modules`, and the resulting type-identity
clash is why patch P-001 exists.

### Known deviation: portalled overlays remain viewport-fixed

"The editor mounts inside its root container" holds for **layout flow**. It does not hold for Radix
dialogs, dropdowns, sheets and toasts, which portal to `document.body` and position themselves
`fixed` relative to the viewport (`components/ui/{dialog,alert-dialog,sheet}.tsx`,
`components/ui/toast.tsx`).

This is a genuine embedding concern, and it is recorded rather than fixed: making overlays
container-relative would change dialog behaviour in **both** hosts, which would damage the parity
reference for no acceptance-criterion gain. An embedder that mounts the editor in a small panel today
will see dialogs centred on the browser window, not on that panel.

## 2. Entry and editor-source import inventory

The final Vite build has two explicit Rollup HTML entries. `index.html` → `src/main.tsx` is the
normal app entry. `surface-evidence.html` → `src/surface-evidence-main.tsx` is an evidence-only
entry used by the dual-Host browser matrix; the normal app does not link to or navigate to it.
`dist/module-graph.json` records the union of both entries, so the measured count above is honest
about verification code that the build emitted.

The ordinary editor route imports twelve editor-source modules through `app.tsx`, the project
picker, and the Vite Host composition chain:

| `@/editor/use-editor`                                | `useEditorInstance`                           | Project-list access through the current session       |

The evidence-only entry shares the two UI providers and `vite-host-config.ts` with the normal Host,

| Evidence entry          | Exclusive editor-source root                                      | Role                                                        |
| ----------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------- |

The pre-existing query-gated C3/C4/C6 proof branches remain statically attached to `app.tsx`, so
their modules also appear in the emitted union graph. They are verification routes, not additions
to the ordinary Host API or to the evidence-only Surface entry above.

**This is not a published API.** There is no `exports` map, no entry point and no stability promise;
the example reaches in through a path alias. Designing the real export surface is later work.

### Dependencies the example had to declare explicitly

Bun hoists workspace dependencies to the root `node_modules`, so `apps/web`'s dependency closure
resolves for the example without being redeclared. Every package the example declares is therefore
either its own build tooling or a **deduplication requirement**, not a hoisting failure:

| Package                                                                           | Why declared                                                                                                                                             |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vite`, `@vitejs/plugin-react`, `vite-plugin-wasm`, `vite-plugin-top-level-await` | The example's own build tooling; `apps/web` has none of it                                                                                               |
| `react`, `react-dom`                                                              | Also in `apps/web` at the same range. Declared so `resolve.dedupe` has a single copy to converge on — two React copies break hooks at runtime            |
| `tailwindcss`, `@tailwindcss/postcss`, `postcss`                                  | Same versions as `apps/web`, deliberately: using the identical CSS pipeline removes "the parity difference is a CSS engine difference" as an explanation |
| `@types/react`, `@types/react-dom`                                                | Type resolution for the example's own sources                                                                                                            |

**No package had to be duplicated because hoisting failed.** That is a positive portability signal,
and the absence of a workaround here is worth as much as the workaround would have been.

## 3. Browser persistence — production `ProjectStore` boundary

`apps/web/src/services/storage/browser-project-store.ts` is the production implementation of the
mechanism-neutral store contract in `apps/web/src/editor/ports/project-store.ts`. IndexedDB, OPFS,
quota inspection, database/path identity and legacy migration stay inside
`apps/web/src/services/storage/`; editor production modules receive the store through their owning
session and never import a browser mechanism or process-global service.

Both Vite and Next composition roots construct one module-stable `BrowserProjectStore` with the
explicit production durable identity, then assign it after the in-memory reference spread. Sessions
created by one Host therefore share only committed durable state; their coordinator, decoded
snapshots, caches, listeners and command queues remain session-owned. `BrowserHostAdapter` has been
deleted and is not part of the export surface.

### Physical cleanup is authorized by mutation granularity

The browser store has one private topology policy between authenticated logical plans and the
IndexedDB/OPFS mechanisms. An authentic descriptor, certificate or journal tuple is necessary but
is not sufficient authority when its target aliases another domain's destructively owned resource.
Library authority is one exact `(database, store)` pair; media cleanup owns one whole database and
one exact OPFS root; migration cleanup owns whole databases. A successful check returns a frozen,
normalized permit, and mutation executes only the targets in that permit instead of deriving names
again after authorization.

For a configured projects database and public projects store, five exact pairs are reserved: the
public store itself and `${projectsStore}-cascade-maintenance`,
`${projectsStore}-media-ownership`, `${projectsStore}-library-clear-bindings`, and
`${projectsStore}-migration-maintenance`. A library cannot use one of those pairs or either
canonical migration-stage database. Sharing the projects database is nevertheless valid when the
library store is distinct from all five reserved stores: library operations are exact-store scoped,
so a database-name-only refusal would reject a safe Host configuration.

Media access and cleanup cannot claim the projects database, a current or strictly retained library
database, either canonical migration-stage database, a migration-owned legacy timeline database,
or a different current/retained media owner's exact database or OPFS root. Migration cleanup cannot
claim live projects or current/retained library or media databases; a canonical stage database may
be deleted only by its matching stage claim after the complete plan is authorized. Ordinary
attachment access and ownership refresh authorize the candidate against all current and retained
media/library claims before registration, descriptor/certificate writes, IndexedDB open or upgrade,
or OPFS access. Current project removal and projects/all clear likewise authorize the complete plan
before project deletion, tombstone/journal commit, store clear, or physical I/O, so a later
collision-free configuration can safely reuse the same project identifier.

Historical cleanup does not gain authority by already being durable. A strictly decoded and
authenticated cascade or migration journal is preflighted as one batch. If any target conflicts,
no target runs, the exact journal is retained without shrink or rewrite, and an existing same-project
save block may remain. A safe retry by the same logical owner over the same exact physical tuple
remains idempotent; intrinsically unsafe historical authority is not automatically remapped or
declared converged.

`script/check-storage-boundary.mjs` inventories every existing module below `apps/web/src` and
`apps/vite-example/src`, including tracked and uncommitted files. Direct `storageService` imports and
`BrowserHostAdapter` references are reported independently from mechanism calls. Browser mechanisms
are permitted only in `apps/web/src/services/storage/**` and these three exact verification programs;
there is no directory or glob exemption:

- `apps/vite-example/tests/parity/snapshot.ts`
- `apps/vite-example/tests/probe/seed.ts`
- `apps/vite-example/tests/probe/legacy-migration.pw.ts`

Persistence `localStorage` is limited to explicitly classified shell/UI preferences: changelog and
mobile-gate acknowledgements, feedback history, generic form persistence, onboarding through the
generic local-preference hook, and persistence-prompt dismissal. Saved sounds and custom graph
presets are durable library records and are deliberately absent from that allowlist.

Project content crosses the public store boundary as an opaque payload plus a typed summary. The
session coordinator retains a complete structured-clone-compatible snapshot and overlays known
project, scene, track, clip, attachment and library edits by stable identity. Retained identities
keep provider-private siblings; deleted identities lose them; new identities cannot inherit them.
Browser-store inputs and outputs are defensively cloned, and failure diagnostics carry only the
operation, scope and stable error code rather than a payload or provider-private exception detail.
Topology refusal follows the same public rule: it is a mechanism-neutral `unavailable` result.
Maintenance emits a fixed topology phase with `retryable: false` and does not expose a physical
database/store/directory name, internal topology reason, provider-private value or raw platform
cause.

Migration is bound to the configured durable identity. Before candidate migration-source discovery
it derives and freezes the complete plan: current/retained media and library claims, stage and
cleanup targets, and every possible v1 transformer source, including legacy timeline and media
databases.
The whole batch is authorized before a transformer can open or upgrade IndexedDB, before attachment
discovery, and before owner registration, stage writes, recovery/cleanup intent, deletion or journal
shrink. Each transform-time source callback must match the frozen source permit. Source access is
read/transform authority only and does not grant deletion: cleanup executes only the separately
authorized cleanup targets.

After that preflight, migration stages legacy projects and attachments, reads the stage back,
commits the current representation, reads the commit back, and only then attempts legacy deletion.
A pre-commit transformation, write or validation failure leaves the source readable and retryable.
A post-commit cleanup failure keeps the committed result and emits a retryable diagnostic.
Destructive migration probes require an exact randomized `c5-disposable-<uuid>` opt-in; the
production identity is never a test cleanup target.

`script/check-port-boundary.mjs` rejects OpenCut schema, command, state-store, browser implementation,
database/store/path and browser-mechanism leaks from the public contract. Separately,
`script/check-host-composition.mjs` proves both production roots final-override reference storage and
rejects a missing override, fallback expression, adapter resurrection, optional Host resolution,
second storage/media port, hidden Host property or private storage context. Capacity estimates remain
nullable; a Host renders "unknown" rather than a confident `0 MB` when the browser supplies no
estimate.

## 4. Runtime assets

`publicDir` is disabled. Assets are copied from `apps/web/public` by an explicit allowlist in
`apps/vite-example/build/editor-assets.ts`, and **that same list is emitted as
`dist/asset-manifest.json`** — so the allowlist _is_ the manifest and there is no second inventory to
drift. An asset the editor needs but the list omits fails at runtime instead of shipping silently.

Copied: `fonts/**` (font atlas + 15 AVIF chunks), `flags/**`, `effects/preview.jpg`,
`logos/opencut/**`, and `favicon.ico` (host chrome, marked as such in the manifest). **297 files,
4.27 MB**, against 4.71 MB across all 335 files in `public/` — the same total
[`SOURCE_INVENTORY.md`](SOURCE_INVENTORY.md) records for that directory. Both figures are content
bytes at 2²⁰ to the MB, which is how `check-asset-manifest.mjs` reports them.

Excluded with recorded reasons: `shapes/` (the shapes sticker provider generates SVG presets in code;
nothing fetches `/shapes`), `platform-guides/` (guide artwork loads from remote `cdn.brandfetch.io`),
`open-graph/`, `landing-page-dark.png`, `logos/others/`, `icons/`, `manifest.json`,
`browserconfig.xml`, `_headers`.

### A missing asset does not produce a 404

`script/check-asset-manifest.mjs` verifies every manifest entry against a running preview server, and
it deliberately does **not** judge by status code. A static SPA host answers any unknown path with
`index.html` at HTTP 200 — measured on this build, `/shapes/circle.svg`, `/platform-guides/x.png` and
`/open-graph/default.jpg` all return **200 `text/html`** despite being genuinely absent. A network
capture showing "no 404s" therefore proves much less than it appears to. The check discriminates on
`content-type` and byte length instead, and separately asserts the excluded paths _do_ fall through
to the HTML fallback.

This is the same failure mode that makes a missing `/api/sounds/search` surface as a JSON parse
error rather than an HTTP failure, which is why server-backed features gate on _configured
endpoints_ rather than on request failure.

### Emitted assets

The manifest also records what the bundler produced: **302 files, 30.70 MB**. The dominant entry is
`ort-wasm-simd-threaded.jsep.wasm` at **21.6 MB**, from `@huggingface/transformers` via the
transcription worker — roughly seven times `opencut_wasm_bg.wasm` (3.04 MB).

It is emitted into `dist/` but is **not on the initial load path**. Verified three ways on the
production build: the entry chunk contains zero references to it; the built `index.html` preloads
only the entry JS and CSS; and a full network capture of loading the app and opening a project never
requests it. The transcription Worker is constructed on demand inside
`services/transcription/service.ts`, so the ONNX runtime is fetched only if transcription is used.

**These are recorded measurements, not claims of adequacy.** No performance or bundle-size claim is
made anywhere in this work.

## 5. Finding: the editor crashes when no GPU is available, in **both** hosts

Spec §3.4 requires a _visible diagnostic_ rather than a blank editor. Testing that path rather than
asserting it from source turned up a real defect.

Running the production build in Chrome with `--disable-gpu --disable-software-rasterizer`
(`navigator.gpu` present, WebGL2 absent), the editor mounts, renders "Loading project…", and then the
entire React tree **unmounts, leaving a blank page**. `DegradedRendererBanner` never appears, because
the tree is gone before it could render. The console shows:

```
GPU renderer unavailable: Failed to create a WebGPU surface: … webgl2 not available …
Failed to generate project thumbnail: GPU context not initialized. Call initializeGpu() first.
```

**This is upstream behaviour, not something this work introduced.** The same run against the
production `next build` + `next start` of `apps/web` fails identically, surfacing Next's built-in
_"Application error: a client-side exception has occurred"_. Both hosts run the same editor source,
and neither reaches editor chrome. The only host-attributable difference was that Next ships a
framework-level error boundary and a bare Vite host does not.

So the example gained `src/editor-error-boundary.tsx` — **host code only, no change to editor
behaviour**. It catches the crash and shows the error message plus `window.__wasmPanic` if one was
recorded, which restores §3.4's "visible diagnostic instead of a blank editor" for this host. It
deliberately does not attempt to prevent or recover from the crash; doing so would change editor
behaviour and cost the parity reference.

Two things remain unverified and should not be read as passing:

- **`DegradedRendererBanner` has never been observed.** Reaching it requires `isGpuAvailable()` to be
  false _without_ the bootstrap crashing first, and no configuration producing that has been found.
- **The `window.__wasmPanic` channel has never been triggered.** It was readable throughout (value
  `null`), but this failure is a WebGPU _surface_ error, not a Rust panic, so nothing ever wrote to
  it. The channel's plumbing is intact; its end-to-end behaviour is untested.

## 6. Provider-private headless editing and attributable proof builds

The observed C7 headless owner is a provider-private session path at
`apps/web/src/editor/session/headless.ts`. It is not re-exported from the public session barrel and
accepts one already-complete `EditorHost`; there is no partial-Host cast or fallback store. Its
surface is deliberately limited to `load`, `save`, and asynchronous `dispose`. Each owner creates
one `SessionPersistenceCoordinator`, scopes operations to the Host project ID, serializes admitted
work, closes admission synchronously on first disposal, and returns one stable terminal disposal
promise. The ordinary full-session factory and the headless factory both call the same
`migration-gate.ts` promise memo, so same-store callers join one migration while a failed attempt is
removed for retry.

The two proof Hosts use one shared graph-envelope checker, but their producer facts are different:

- Vite builds a dedicated `headless.html` facade. Rollup records the exact entry's outgoing closure
  and emitted chunk membership during `generateBundle`; `writeBundle` then reads the final HTML and
  output bytes from disk. The envelope carries the HTML digest, every observed script link, and the
  exact entry chunks. The checker re-reads the HTML and rejects missing or altered bytes, scripts
  outside the output, and a module script that does not load the exact entry chunk.
- Next uses explicit Webpack only when `OPENCUT_C7_HEADLESS_PROOF=1`. The ordinary configuration has
  no Webpack callback, retains standalone output, and was observed selecting Next 16.1.3 Turbopack.
  The proof collector locates `app/c7-headless/route` exactly once, requires actual chunk-graph
  membership from that module or its concatenated owner, intersects those chunks with the named
  Webpack entrypoint, and traverses outgoing dependency edges while retaining only modules with
  emitted ownership. Entry-point filenames alone are not accepted as root membership. Compiler-
  emitted server WASM is copied only within the validated proof output root to the runtime lookup
  location, and the mirror records the identical byte digest.

Both executable entries install `headless-runtime-probe/v1` before dynamically loading the semantic
fixture. The probe records ordered install/load/bind/finish/restore events; exact Host, project and
store-instance binding; global timer/RAF/Worker/AudioContext/object-URL/WebGPU/WASM calls; Host
resource-factory and graphics calls; final in-memory resource counts; and React DOM mutations/root
markers (or the explicit server-no-DOM observation). The semantic evaluator derives its zero-use
claims from that attributed snapshot and rejects missing observations, reordered provenance,
fallback stores, fabricated summaries, or Host/result/graph identity reuse.

`SOURCE_INVENTORY.md` and `SOURCE_INVENTORY.json` are intentionally not regenerated in the
uncommitted implementer tree. Their generator obtains fork additions with `git diff --name-status`
against the upstream pin; C7's new files are still untracked and would therefore be omitted. The
local Luna ship leaf must first create the reviewed child commit, then regenerate and verify the
official inventory against that committed tree. Until that leaf completes, the authored-path
manifest and content digest in the C7 evidence are the truthful pre-commit inventory; no official
source-inventory pass is claimed.

## 7. Package boundary (S05 P0)

`packages/` declares three publishable packages and holds no source yet — `apps/web/src` still owns
every module, through the existing `@` path alias. This section is that declaration, the measurement
that forced its shape, and what it does not yet cover. Implementation (moving source, publishing) is
later work; this is the freeze the later work is held to.

### Three packages, ports at the bottom

```
0  @opencut/editor-ports        editor/ports/** and editor/host/editor-host.ts — no dependencies
1  @opencut/editor-contracts    editor/contracts/** — depends on layer 0 only
2  @opencut/editor-classic      everything else under apps/web/src — depends on layers 0 and 1
—  apps/web, apps/vite-example, P2's second Host   consumers; not packages; may depend on any layer
```

The intuitive reading of "contracts / ports / surface" puts contracts underneath ports. The measured
import graph (948 source files under `apps/web/src` and `apps/vite-example`, parsed for every
`import` / `export … from` / `require()` / dynamic `import()` specifier) says the opposite: **8**
production edges run `editor/contracts/**` → `editor/ports/**`, and **0** run the other way.
`contracts/engine` and three other contracts modules consume `IdGenerator` and `DiagnosticsPort` from
ports; nothing in ports needs a domain type. Ports sits at the bottom because it is the one complete
surface a Host author implements — zero dependencies, no React, no DOM (spec §3.5, mechanically) —
and contracts is the one thing that depends on it, not the reverse.

Above that two-layer base, the rest of the tree is one dense mutual-recursion knot in production
code, measured the same way:

| candidate seam | A→B (prod) | B→A (prod) |
| --- | ---: | ---: |
| Classic provider ↔ editor UI | 228 | 293 |
| editor UI ↔ session/runtime | 95 | 17 |
| session/runtime ↔ Classic provider | 64 | 31 |
| editor UI ↔ `editor/surface` | 19 | 16 |
| `editor/surface` ↔ Classic provider | 5 | 1 |

Every one of those five seams is bidirectional in production source, including the smallest —
`editor/surface` ↔ UI is two layers wearing one name, not an accident. Cutting any of them apart
requires inverting production dependencies, which is a rewrite, not an extraction: P1 is constrained
to a behaviour-preserving move whose oracle is the parity fixture, and a rewrite would trade that
guarantee for a diagram. So everything above the ports/contracts base is one package,
`@opencut/editor-classic`, split internally by `exports` subpath rather than by package.

### `editor/host/editor-host.ts` belongs to ports, and resolves a live cycle

`ports/index.ts` re-exports `EditorHostNavigation` from `../host/editor-host` under the frozen name
`NavigationHost`, while `editor-host.ts` itself imports `@/editor/ports` — a live module cycle today,
harmless only because both directions are type-only. Splitting `editor/ports/` and `editor/host/`
into different packages would turn that into a package cycle, which is exactly what the
`acyclic-direction` rule below forbids. `editor-host.ts` is 118 lines, imports nothing but
`@/editor/ports`, contains no React and no DOM, and is in substance a ports module; assigning it to
`@opencut/editor-ports` resolves the cycle without editing the frozen `NavigationHost` re-export. The
rest of `editor/host/` does not follow it — browser and React modules go to `@opencut/editor-classic`,
Next-Host composition stays in `apps/web`.

### The checker: `script/check-package-boundary.mjs`

Five rules, three live today and two dormant until `packages/` gains source:

| rule | status | what it asserts |
| --- | --- | --- |
| `acyclic-direction` | live | every cross-package edge points to a strictly lower declared layer |
| `no-elftia-import` | live | no package, Host or example imports an Elftia package, protocol identifier or runtime object |
| `react-free-base` | live | `editor-ports` and `editor-contracts` import no React, no DOM global, and no `editor-classic` module |
| `public-entry-only` | dormant, `0 files scanned` | a specifier into a package resolves only to a declared `exports` subpath |
| `no-internal-reexport` | dormant, `0 files scanned` | no declared entry re-exports another package's undeclared internals |

Ownership is resolved from `packages/boundary.json`, a committed, longest-prefix-wins map from path
to package with a required `why` per entry — the same self-guard idiom `check-next-imports.mjs`
applies to its own allowlist: the checker refuses to run if any declared consumer path (`app/`,
`site/`, `blog/`, `db/`, `auth/`, `components/landing/`) resolves to a package instead of a consumer,
and refuses to run if any tracked file under `apps/web/src` resolves to no owner at all. Both dormant
rules report their `0 files scanned` census as explicit output, not a silent `PASS` — a check that is
green because it inspected nothing is not the same claim as a check that is green because it looked.

**The Elftia rule matches specifiers, dependency names and identifiers — never raw file text.** A
substring scan over `elftia` is wrong in this repository in both directions: eight tracked files
(`editor/ports/DECISIONS.md`, `apps/vite-example/README.md`, `editor/session/resources.ts`, three
`ports/*.ts` compile-guard/documentation files, and `script/check-port-boundary.mjs`) contain the
word `elftia` in prose, all of it explaining *why the ports are Elftia-neutral* — a text scan would
flag the documents that record the boundary. So the rule matches only: import specifiers (`elftia`,
`elftia/*`, `@elftia/*`, `^elftia-plugin-`); dependency names in every `package.json` and package
identifiers in `bun.lock`; the protocol literals `plugin://` and `elftia://`; and the runtime
identifiers `window.elftia`, `globalThis.elftia`, `window.native`, `window.api`, `CapabilityBroker`,
`ArtifactRuntime`, `ArtifactRef`. There is no `adapter-elftia` exception: it does not exist in this
repository, and housing one here would make the portable SDK depend on its largest consumer.

The DOM check inside `react-free-base` is identifier-level for the same reason a text scan would be
wrong: `document` is a domain term throughout `editor/contracts` (a local draft-document value in
`draft` and `engine`, a parameter name across `vectors/**`, and the family literal
`"document" | "scenario"` in `vectors/schema.ts`) — the exact package this rule protects. A file that
visibly declares `document` as a local name has its bare `document` references read as that local,
not the DOM global; `document` inside a quoted string is never an identifier at all. `window.document`
still fires regardless, since `window` alone triggers the match.

Both `--negative-control` (synthesises one violation per rule and asserts it is caught) and
`--converse-control` (synthesises a legal case per rule and asserts it stays silent) run the same pure
`scan()` against in-memory fixtures, so every rule — including the two dormant ones — is fully
control-tested today, before `packages/` holds a single real file.
