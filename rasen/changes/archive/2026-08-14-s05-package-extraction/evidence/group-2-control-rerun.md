### Finding: `--regenerate` is not safe to run casually against this fixture

While confirming task 2.5's instrumentation, `node script/check-type-baseline.mjs --regenerate` was
run once to see whether the committed fixture should also carry a pin-side file count. It reported
**32 diagnostics (25 distinct)** at the pin — not the 13 the committed
`script/fixtures/type-baseline.json` records. `git diff` (the fixture is tracked) showed the delta
was not merely additive: 19 diagnostics not in the committed fixture, including three
`.next/types/app/<route>/page.ts` / `.next/types/validator.ts` `TS2307` "cannot find module" errors
naming the routes `c6-disposal`, `c7-headless`, `surface-evidence`, plus several React ref-typing
`TS2322`/`TS2540` errors under `src/preview/` and `src/timeline/`.

Root cause, confirmed rather than assumed:

```
$ git ls-files apps/web/src/app | grep -E "c6-disposal|c7-headless|surface-evidence"
apps/web/src/app/c6-disposal/page.tsx
apps/web/src/app/c7-headless/route.ts
apps/web/src/app/surface-evidence/page.tsx
$ git ls-tree -r --name-only cf5e79e919144200294fb9fed22a222592a0aeea -- apps/web/src/app \
    | grep -E "c6-disposal|c7-headless|surface-evidence"
(no output — none of the three exist at the pin)
```

`apps/web/.next` is gitignored, ambient, machine-local build output (`apps/web/.gitignore:8`), last
built locally **after** these three routes existed. `reconstructPin()` links the *current*
`apps/web/.next` wholesale into the reconstructed pin directory (by design, documented in the
script's own header: rebuilding it would manufacture differences unrelated to source edits). But
`.next/types/app/<route>/page.ts` files are per-route validator stubs generated by Next itself, each
containing a relative import back to that route's `page.tsx`. Linked into a pin whose `apps/web/src`
predates those three routes, the validators point at source files that don't exist there — a false
`TS2307` with nothing to do with any Slice edit. The React ref-typing errors are most likely the same
shape one layer down (a dependency version resolved into the shared, linked `node_modules` sometime
after the original fixture was captured, checked against the pin's older source) but this was not
traced further — establishing the `.next` mechanism alone was sufficient to disqualify the result.

This means: **whoever next runs `--regenerate` on this fixture will reproduce the same false
32-diagnostic blowout**, unless `apps/web/.next` is rebuilt fresh from HEAD first (or removed and
left unbuilt, if the script tolerates that — not tested here). This is pre-existing fragility in
`reconstructPin()`'s method (task 1.1-era design, not introduced by Group 2's edits), latent until
someone actually re-regenerates. Recorded as a finding for task 9.4 and for whoever holds
`check-type-baseline.mjs` next: **do not regenerate this fixture without first confirming
`apps/web/.next` was built from the current `HEAD`, or better, deleting it and letting a fresh
`next build`/`next dev` warm-up regenerate it immediately before `--regenerate` runs.**

The committed fixture (`script/fixtures/type-baseline.json`) was **not** touched by this finding —
`git checkout -- script/fixtures/type-baseline.json` reverted the regenerate output immediately after
the discrepancy was noticed, before drawing any conclusion from it. `git status --porcelain` for that
path is clean. Only the normal (non-`--regenerate`) comparison mode was used for every measurement
recorded in this evidence file and in `group-2-type-baseline-reach.md`.
